## 二、产品定义

### 2.1 产品目标（一句话）

> 让「备份插件」的安装目标从平台主机改为**可指定的 SSH 数据库服务器（服务端）**，使外部物理备份工具真正落到远端并能在调度时被服务端检查/调用，从而让物理备份任务在服务端真实可执行。

三个正交的可量化子目标：

1. **装对地方**：安装器能通过 SSH 把插件（离线包 SFTP 上传 / 远端 apt·yum）安装到用户指定的 SSH 主机上，而非平台主机。
2. **判对对象**：调度前检查（preflight）从「查平台主机」改为「查服务端」是否有对应工具，杜绝"平台装好、远端没装"导致的物理备份失败。
3. **看对状态**：插件安装状态按「主机」维度记录与展示，运维能一眼看清"哪台服务器装了哪些插件"。

### 2.2 用户故事

1. **作为运维**，我在「备份插件」页选择目标 SSH 主机（如 192.168.220.133 MySQL 服务器），把 xtrabackup 一键安装到该 MySQL 服务器上；安装完成后，这台主机的 MySQL 物理备份任务就能在服务端真实执行，不再因"平台装了、远端没装"而失败。

2. **作为运维**，我发起一次 MySQL 物理备份调度时，系统在调度前自动检查**目标数据库服务器**上是否存在 xtrabackup；若不存在则明确报错并提示"前往备份插件页为该主机安装 xtrabackup"，而不是给出误导性的"平台主机已就绪"。

3. **作为 DBA**，我在「备份插件」页可以逐台查看每台已纳管 SSH 主机的插件安装状态（已装/未装/安装中/失败），并能一键安装某台主机上"所有已配置数据库任务所需"的插件。

## 三、技术规范

### 3.1 需求池（Requirements Pool）

> 优先级约定：P0 = 必须（否则物理备份无法正确落地）；P1 = 应当（体验/可观测性关键）；P2 = 可选（效率增强）。

| 优先级 | 需求 | 说明 / 验收要点 |
|---|---|---|
| **P0** | **插件安装目标改为"可指定 SSH 主机（服务端）"** | `plugin_installer.install()` 增加 `host_id`（或 `host_key`）入参；通过 SSH/SFTP 在远端执行安装：离线包先下载到平台再 SFTP 上传到远端解压，或远端直接执行 apt/yum 安装命令。`detect_os()`/`detect_package_manager()` 改为探测**远端 OS/包管理器**（复用 `ssh_hosts` 与 `remote_dump._resolve_remote_bin` / `remote_has_tool` 的既有 SSH 通道）。安装日志/状态文件仍落平台，但安装产物在远端。 |
| **P0** | **物理备份工具分类：数据库自带 vs 外部插件** | 明确两类工具：①「数据库自带工具」——Oracle `rman`、PG `pg_basebackup`、Kingbase `sys_basebackup`、达梦 `dmrman`、MySQL `mysqldump` 等，**直接 SSH 到数据库服务器执行，不走插件**；②「外部插件」——`xtrabackup` / `mariabackup` / `pgbackrest` / `mongodump` / `redis-cli` 等，**必须先装到服务端再执行**。物理备份调度根据任务类型分流：自带工具走既有远端执行路径；外部插件先校验服务端是否已装，未装则报错引导安装。 |
| **P0** | **preflight / 调度前检查对象改为服务端** | `base.preflight()` / `check_client()` 中 `shutil.which()` 检查的"本机 PATH"逻辑，在物理备份场景改为调用 `remote_dump.remote_has_tool(ssh_host, tool)` 或 `_resolve_remote_bin(client, tool)` 检查**远端服务器**；未纳管 SSH 主机或远端缺工具时，返回明确错误（"远端未安装 X，请到备份插件页为该主机安装"）。逻辑备份本机检查逻辑可保留作为兜底。 |
| **P1** | **插件安装状态按「主机」维度记录** | 状态文件/DB 记录从"插件 id"扩展为"插件 id + host_key/host_id"二维；记录每台主机装了哪些插件、状态（installed/uninstalled/installing/failed）、版本、时间。`check_installed` / `list_plugins` 支持按主机查询，而非只查平台本机。 |
| **P1** | **「备份插件」页支持选择目标主机查看/安装** | 前端 `/plugins` 页增加「目标主机」下拉（数据源为 `ssh_hosts.list_hosts()`），展示每台主机的插件安装状态矩阵；安装按钮文案明确"将安装到目标主机 X"，避免误装到平台主机。 |
| **P2** | **一键安装某主机"已配置任务所需"插件** | 提供"按主机一键补齐"入口：根据该主机上已配置的数据库任务类型（db_type）自动计算所需外部插件清单，批量下发安装（复用 `recommend_for_host` 的 db_type 匹配逻辑，改为按远端主机维度）。 |

### 3.2 UI 设计稿（文字描述）

**「备份插件」页（改造后）**

```
┌─────────────────────────────────────────────────────────────┐
│  备份插件                                                     │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │ 目标主机：[▼ SSH 主机下拉：全部 / 192.168.220.129(Oracle)│ │
│  │           / 133(MySQL) / 150(MySQL+file) ]   [刷新状态]  │ │
│  └─────────────────────────────────────────────────────────┘ │
│                                                               │
│  主机：192.168.220.133（MySQL）                                │
│  ┌──────────────┬──────────┬────────┬──────────────────────┐ │
│  │ 插件名        │ 状态     │ 版本    │ 操作                  │ │
│  ├──────────────┼──────────┼────────┼──────────────────────┤ │
│  │ XtraBackup 8 │ 未安装   │ —      │ [安装到目标主机]       │ │
│  │ XtraBackup 2.4│ 已安装  │ 2.4.29 │ [卸载]  [查看日志]     │ │
│  │ mariabackup  │ 安装中   │ —      │ (进度条/轮询日志)      │ │
│  │ pgbackrest   │ 不适用   │ —      │ (该主机无 PG 任务)     │ │
│  └──────────────┴──────────┴────────┴──────────────────────┘ │
│                                                               │
│  [一键安装本主机已配置任务所需插件]                              │
└─────────────────────────────────────────────────────────────┘
```

要点：
- 顶部「目标主机」为必选/可切换；选择后下方插件列表与安装状态随之切换为该主机的数据。
- 每个插件的「安装」按钮文案明确为"安装到目标主机 X"，并有二次确认提示"该操作将在远程服务器 X 上执行安装命令"。
- 安装状态沿用既有轮询机制（后台线程 + 状态文件），但状态文件以 `host_key + plugin_id` 为键。
- 平台主机（本机）作为可选的特殊"目标主机"保留，但默认提示"数据库插件建议安装到数据库服务器"。

### 3.3 待确认问题（Open Questions）

1. **离线包传输方式**：插件离线包是"平台主机下载后 SFTP 上传到远端解压"，还是"远端直接 `wget`/`curl` 下载"？若远端无外网，是否要求平台侧预先缓存离线包并走 SFTP？（涉及 `_download_and_extract` 改造范围）
2. **远端安装状态回传与持久化**：远端装完后的"真实就绪"状态如何回传记录——是在远端执行 `verify_after_install`（如 `xtrabackup --version`）后回传结果，还是仅信任安装命令退出码？状态是否需要落 SQLite 表（而非仅状态文件），以便跨进程/重启后仍可见？
3. **包管理器 vs 离线包的优先顺序**：远端 `detect_package_manager()` 如何实现（复用 `remote_has_tool` 逐个探测 apt/yum/dnf？），以及离线包解压目录（`/opt/...`）是否固定、是否需要 sudo 权限？
4. **调度前检查的失败策略**：远端缺工具时，是"硬失败并阻止调度"还是"允许调度但任务运行时报错"？是否需要新增"自动安装缺失插件"的调度前联动（风险较高，建议仅提示）？
5. **数据库自带工具的覆盖范围**：确认自带工具清单是否完整（Oracle rman / PG pg_basebackup+pg_dump / Kingbase sys_basebackup+sys_dump / 达梦 dmrman+dexp / MySQL mysqldump / Redis redis-cli / MongoDB mongodump？），其中 redis-cli、mongodump 目前被归为"外部插件"，需确认与「数据库自带」边界是否统一。
6. **多主机同名插件与幂等**：同一插件在多台主机上独立安装，卸载/升级时是否逐主机操作？重复点击安装的幂等判定改为按 `host_key + plugin_id` 维度。
