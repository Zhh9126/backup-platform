# 备份存储管理（三重备份体系）PRD

> 版本：v1.0　|　作者：产品经理 许清楚　|　适用范围：备份管理平台（Flask + SQLite + APScheduler，Bootstrap5 + 原生 JS）
> 关联代码：现有 `core/storage.py`（本地 + SFTP）、`config.py` 中 `REMOTE_DEFAULTS`；参考项目 `E:\databasus-main\databasus-main`（存储后端抽象 / 任务分发 / 归档策略）

---

## 1. 产品目标

在现有备份平台之上引入「三重备份体系」：所有备份先落盘到第一级 MinIO 热数据层，再由第二级准实时推送到远程对象存储（S3 兼容，冷数据/异地容灾），并可选第三级导出到服务端本地路径供离线转移，从而实现"一处产出、多级冗余、冷热分离、可审计可恢复"的备份存储架构。

---

## 2. 用户故事

- **故事 1（容灾管理员）**：作为容灾管理员，我希望备份完成后能自动同步到异地对象存储，这样即使机房级故障导致本地 MinIO 不可用，我仍能从 S3 恢复数据，满足异地容灾要求。
- **故事 2（存储运维）**：作为存储运维，我希望在 Web 上集中配置并监控 MinIO / S3 / 本地导出路径三套存储后端的状态与用量，这样我无需登录多台服务器即可发现容量不足或推送失败。
- **故事 3（合规审计）**：作为合规人员，我希望每条备份记录都能清楚看到其在三级存储中的分布（已落盘 / 已推送 / 已归档）与校验值，这样在发生恢复需求时能快速定位可信副本并满足审计留痕。

## 3. 需求池（P0 / P1 / P2）

### P0（必须，首版交付）
| 编号 | 需求 | 说明 / 验收 |
|---|---|---|
| S-01 | 第一级 MinIO 热数据层 | 所有备份产出先写入 MinIO（bucket + 前缀），作为主可读存储层；提供连接配置（endpoint、access_key、secret_key、bucket、region、是否启用 TLS）。 |
| S-02 | 第二级 S3 兼容冷数据层 | 第一级落盘后准实时推送至 S3 兼容对象存储（AWS S3 / 阿里云 OSS / 腾讯云 COS / MinIO 远端等），用于异地容灾与长期归档。 |
| S-03 | 第三级本地路径导出 | 可选启用一个服务端本地路径，将备份导出到该目录供用户离线转移到别处；支持开关与路径配置。 |
| S-04 | 统一存储后端抽象 | 借鉴 databasus 的存储后端抽象，定义 `StorageBackend` 接口（put / get / delete / exists / list / stat），MinIO / S3 / Local 各自实现，与第一级落盘解耦。 |
| S-05 | 推送链执行顺序 | 严格保证"先到第一级 → 再由第二级实时推送到二、三级"；任一级失败不影响前级已落盘数据，但需记录状态并触发重试/告警。 |
| S-06 | 推送状态机与落库 | 每条备份记录在元数据中记录三级存储状态（pending / uploading / done / failed），与现有 `core/storage.py` 的保留策略打通。 |
| S-07 | 失败重试 | 推送失败按指数退避重试（默认 3 次），全部失败进入告警队列。 |
| S-08 | 存储配置页 | 在「设置」下新增「存储管理」页，集中配置三级存储后端与推送策略。 |
| S-09 | 推送失败告警 | 复用现有 `notifier.py`（webhook/钉钉/企微/飞书/邮件），推送失败 / 存储不可达时按通知开关告警。 |

## 4. 核心流程（一次备份任务经过三级存储）

状态机（单条备份记录 `backup_id`）：

```
[备份执行] 
   │  产出备份文件（本地临时/backups）
   ▼
[第一级 MinIO 落盘]  state = uploading_l1
   │  成功 → 写入 MinIO（bucket=hot, prefix=task/date/）
   │  失败 → state = failed_l1 → 告警（不继续推送）
   ▼ state = done_l1
[第二级 S3 准实时推送]  state = uploading_l2（监听第一级落盘事件 / 调度触发）
   │  成功 → 推送到 S3（冷数据 bucket）
   │  失败 → 指数退避重试（≤3）→ 仍失败 state = failed_l2 → 告警
   ▼ state = done_l2
[第三级 本地路径导出（可选）]  state = exporting_l3
   │  启用时：将文件导出到服务端本地路径（或 SFTP）
   │  失败 → 重试 → 仍失败 state = failed_l3 → 告警（不影响一、二级）
   ▼ state = done_l3 / skipped_l3（未启用）
[完成] 记录三级状态 + 校验和，更新存储统计
```

时序说明：
1. 第一级为**必经**主链路，引擎产出文件后立即由 `StorageDispatcher` 写入 MinIO，成功后才认为"备份可用"。
2. 第二级为**准实时**：由事件总线（或短周期 APScheduler job）监听第一级 `done_l1` 事件触发推送；推送与主备份链路解耦，失败可补推。
3. 第三级为**可选后置**：仅在用户启用且配置合法时执行，失败不阻断一、二级；用于离线/物理转移场景。
4. 任何一级失败均写入 `push_tasks` 重试队列，并依据 `notifier.py` 触发告警。
5. 对账：定时任务扫描 `done_l1` 但 `failed_l2/l3` 的记录，自动补推并汇报。

## 5. 页面与交互（新增 / 调整清单）

- **存储管理页（新增）** `/storage`：三级存储后端的总览与入口，含"添加后端""连通性测试""启用开关"。
- **存储配置模态框（新增）**
  - MinIO 配置：endpoint、access_key、secret_key、bucket、region、use_tls、默认前缀。
  - S3（冷数据）配置：provider 下拉（AWS/Aliyun/Tencent/Generic S3）、endpoint、region、bucket、access_key、secret_key、存储类（Standard/IA/Archive）。
  - 第三级导出配置：模式（本地目录 / SFTP，沿用 REMOTE_DEFAULTS）、路径、SFTP 主机/端口/账号/密钥。
- **存储桶 / 路径管理模态框（新增）**：增删改查 bucket / 前缀 / 本地路径，带"测试连接"按钮与即时反馈。
- **存储状态页（新增）** `/storage/status`：各后端连通性、容量、对象数、最近推送耗时、健康度灯。
- **推送策略配置（新增，并入存储管理）**：并发上限、限速、重试次数、退避基准、是否启用第三级。
- **手动推送 / 重新归档（新增，嵌入备份记录行操作）**：单条/批量"立即推送二级""重新归档三级"。
- **归档与生命周期配置（新增模态框）**：按保留天数/份数对二级冷数据做 lifecycle 规则设置。
- **已有页面调整**：备份记录列表增加"三级存储状态"列（三色/图标：已落盘 / 已推送 / 已归档 / 失败）；仪表盘增加"存储健康"卡片。

交互要点：所有敏感凭据（secret_key、密码、密钥）在表单中掩码展示、回显脱敏，存储沿用现有混淆落库方式，不出现于 URL/日志明文。

## 6. 非功能需求

- **性能**：单条备份第一级落盘不显著增加备份主链路耗时（建议异步写入或缓冲写入，目标 P95 < 备份耗时 + 5%）；第二级准实时推送延迟目标 < 1 分钟（小文件）/ 可配置；大文件支持分片与并发（P2）。并发推送上限默认 4，可配置，避免占满带宽。
- **安全**：传输全程 TLS；静态加密可选（SSE-S3 / SSE-KMS）；凭据脱敏存储与展示；Web 接口沿用现有 `login_required` 鉴权；最小权限原则（存储账号仅授予所需 bucket 权限）。
- **兼容性**：S3 兼容协议覆盖 AWS S3、阿里云 OSS、腾讯云 COS、Ceph RGW、MinIO、Wasabi 等；MinIO 支持内嵌或外置部署；前端 Bootstrap5 + 原生 JS，不引入重型框架；后端沿用 Flask 蓝图与 SQLite 元数据，新增 `storage_backends`、`push_tasks` 表。
- **可扩展性**：存储后端基于 `StorageBackend` 抽象，新增后端（如 Azure Blob、GCS、NAS）只需实现接口并注册，无需改动调度与主链路；推送策略、生命周期策略以配置化驱动，便于后续扩展多目标复制（P2 S-18）。
- **可观测性**：推送成功/失败、耗时、对象大小、校验和写入元数据，供监控页与统计报表消费；与现有通知体系打通。
- **可靠性**：推送失败重试与补推对账，保证最终一致；三级之间幂等写入（同一 backup_id 重复推送可安全覆盖/跳过）。

## 7. 待确认问题

1. **MinIO 部署形态**：内嵌（平台自带 MinIO 进程，开箱即用）还是外置（对接用户既有 MinIO 集群）？两者影响部署复杂度与运维边界，建议首版支持"外置为主、内嵌可选（Docker 一键起）"。
2. **S3 兼容协议范围**：除 AWS S3 外，需明确首版必须兼容的国产云清单（阿里云 OSS / 腾讯云 COS / 华为云 OBS / 火山引擎 TOS）与签名版本（v2/v4），以决定 SDK 与 endpoint 适配范围。
3. **第三级形态**：是仅支持服务端本地目录导出，还是同时支持 SFTP（沿用 `REMOTE_DEFAULTS`）？是否未来需要支持 NAS/NFS 挂载路径或 Azure Blob 等？
4. **推送解耦方式**：采用事件总线（如轻量消息表 + APScheduler 轮询）还是进程内回调？需权衡实时性与部署简单性，倾向"短周期调度轮询 done_l1 事件"。
5. **容量统计来源**：MinIO / S3 的容量与对象数能否通过 API 获取（部分对象存储不开放账户级额度），否则需平台侧自行累计。
6. **加密与密钥**：静态加密是否要求对接企业 KMS（如 HashiCorp Vault / 云 KMS），还是平台自带主密钥即可满足首版？
7. **保留策略冲突**：现有 `core/storage.py` 的本地保留清理与新增第二级生命周期清理的职责边界如何划分（建议：第一级沿用现有清理，第二级由 lifecycle 规则负责）。
8. **权限模型**：是否需要按角色区分"存储配置"与"推送操作"权限（当前为单管理员账号 `admin`），或首版沿用单账号即可。
