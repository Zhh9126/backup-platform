## 全库备份/恢复端到端测试

### 背景
用户要求测试各个数据库的备份任务（全量+增量）和恢复是否正常执行。

### 测试方案
- 新建 `tests/test_backup_restore_all.py`，使用 `DEMO_MODE=on` 强制仿真，无需安装任何 DB 客户端即可验证平台业务逻辑。
- 覆盖 9 种 db_type：mysql, mariadb, postgresql, oracle, kingbase, dameng, redis, mongodb, file。
- 每个类型测试：全量备份 → 记录落库 → 恢复；物理类型(mysql/mariadb/oracle/dameng)额外测真增量链。
- 用临时目录（tempfile.mkdtemp）隔离测试数据，不污染真实库。

### 结果：18 个测试全部通过（Ran 18 tests, OK）

### 重要发现（系统行为）
1. **file 备份是异步的**：`run_task_now` 对 `db_type="file"` 返回 `{"accepted": true, "status": "running"}`，真实 record 由后台线程完成——需轮询 `list_records` 等待完成。
2. **backup_sets 表不常写**：普通 `run_task_now` 不会写 `backup_sets`，只有增量链合成/准CDP 等特定场景才由引擎或 lifecycle 写入。测试备份集断言要小心。
3. **demo 模式忠实保留 backup_type**：`_simulate_backup` 拿到什么 backup_type 就标记什么（full/incremental/snapshot），不会回退。回退逻辑（逻辑引擎 incremental→full）只在真实模式生效。
4. **file 差异备份回退**：file 引擎仿真模式下 differential 回退为 full（占位备份不分差异类型）。
5. **恢复状态**：demo 模式 `run_restore_now` 返回 `status="simulated"`（真实模式为 "success"），测试接受两者。

### 运行命令
```
cd e:\备份管理平台\backup_platform
python tests/test_backup_restore_all.py
```
注意：Windows PowerShell 下读取中文测试结果需 `$env:PYTHONIOENCODING="utf-8"` 或重定向到文件用 python 读。

## 压缩技术增强（zstd，先进算法 + 可恢复 + 可量化压缩率）

### 背景
用户要求：备份磁盘空间有限，引入先进压缩技术；压缩后必须能解压恢复；并输出压缩率。

### 方案
统一在 `core/engines/base.py` 的 `BackupEngine` 增加：
- `pipe_compress(algo, level)` / `pipe_decompress(algo)`：返回可插入「数据管道」的压缩/解压命令。
- 算法优先级：**zstd > gzip**；**全部用 Python 库实现**（`zstandard` / 标准库 `gzip`），不依赖系统外部二进制，Windows/Linux 一致、必定可恢复。若部署机存在系统 `zstd` 则优先使用获得更高吞吐。
- `original_size_bytes` / `compress_algo` / `compress_ratio` 加入 `BackupResult` dataclass。

### 改动文件
1. `core/engines/base.py`：压缩工具 + 字段；`_ZSTD_LEVEL=10`（磁盘极紧张可改 19）。
2. `core/db.py`：`backup_records` 迁移新增 `original_size_bytes / compress_algo / compress_ratio` 三列。
3. `core/scheduler.py`：`_finalize_backup_record` 落库时写入这三列（压缩率=压缩后/压缩前）。
4. `core/engines/mysql.py`：逻辑备份用 `pipe_compress`（tee 旁路记原始大小），恢复用 `pipe_decompress`（支持 .gz/.zst）。MariaDB 继承自动获得。
5. `core/engines/file.py`：`_tar_local`/`_tar_files` 先 tar 未压缩再 zstd 压缩为 `.tar.zst`，记录原始 tar 大小到 `.orig.size`；`_restore_local` 解压 `.zst` 再 extractall；全量/增量/实时 BackupResult 补压缩字段。**注意：file 解压用 `stdin=open(item)` 而非把 item 当参数传给 `python -c` 脚本**（已修复 bug）。

### 物理备份（保持原样，已是 zstd）
- mysql/mariadb 物理：xtrabackup `--compress=zstd`，恢复 `--decompress`。
- oracle/kingbase/dameng：数据库自带工具原生压缩（expdp/sys_dump/dexp 压缩参数）。

### 实测压缩率（基准：`tests/benchmark_compression.py`）
混合数据类型加权综合：
- **gzip -6（原方案）：26.26%**
- zstd level3：25.91% / level10：24.30% / level19：22.36%
- **默认 zstd level10 比 gzip -6 再省 7.5% 磁盘；level19 省 14.8%**。
- 文本/CSV 类可压缩数据收益显著（SQL 文本 zstd19 仅 8.57% vs gzip 11.49%）；随机/已压缩数据本就无压缩空间（正常）。
- 解压恢复：所有样本均通过可逆性校验（OK）。

### 端到端验证
- `tests/test_file_zstd_roundtrip.py`：文件引擎 zstd 压缩→解压恢复，内容校验 OK，压缩率正确记录。
- `tests/benchmark_compression.py`：gzip vs zstd 多级别对比 + 可逆性校验。
- 需先 `pip install zstandard`（仅测试/运行依赖；生产部署机若用系统 zstd 则不必装库）。

### 注意
- Windows 无系统 gzip/zstd 二进制，旧代码 `pipe_compress` 用 `gzip` 二进制会失败；现已全部改为 Python 库实现。
- 若需"压缩率"展示，可新增 API 读取 `backup_records.compress_ratio` / `original_size_bytes`。
