# 对标 zbackup：文件备份去重与形态保真（2026-11-26）

来源：https://github.com/zbackup/zbackup（全局去重备份工具，C++）
用户诉求：「文件的备份可以使用 zbackup 的代码进行优化」「文件里面的各种文件都要
可以进行备份恢复」。

## 一、zbackup 的核心机制（已核实）

| 机制 | 说明 |
|------|------|
| **内容定义分块（CDC）** | 滚动哈希（Rabin）在字节流上找**内容边界**，切成变长块；同一内容段在任何文件/任何偏移都切在同一处 |
| **块级全局去重** | 块以 SHA256 内容寻址入库，重复块只存一份；跨备份集/跨时间共享 |
| **bundle + index** | 块打包压缩（+可选 AES-256）；备份文件只是一串块引用 |
| **流式 stdin/stdout** | `tar … | zbackup backup` / `zbackup restore | tar …` |
| **元数据** | **不备份**（权限/属主/时间戳需另配 tar） |
| **风险** | 去重后无冗余，单块丢失影响面大；单线程；不支持 Windows |

## 二、吸收什么 / 不吸收什么

| 项 | 决策 | 理由 |
|----|------|------|
| CDC 内容定义分块 | ✅ **吸收** | 解决我们 4MB 固定块「归档里一字节变化 → 其后块指纹全移位」的失效问题 |
| 内容寻址块库 + 块级校验 | ✅ **吸收** | 跨任务/跨时间全局去重；重组逐块 sha256 硬校验 |
| **元数据保真** | ✅ **比它强** | zbackup 不管元数据；我们补齐权限/属主/mtime/空目录/软硬链接 |
| bundle 归档格式 | ❌ 不吸收 | 与现有 tar 恢复链不兼容，换格式=全链路重写 |
| 单线程 C++ 二进制 | ❌ 不吸收 | 离线交付要带编译产物+glibc 矩阵；纯 Python 满足 PyInstaller 离线自足 |
| AES-256 落盘加密 | ❌ 不吸收 | 我方已有 SM4 凭据加密 + 存储池加密策略，重复造轮子 |
| 「去重后无冗余」 | ❌ 不吸收 | 我方多副本/池复制语义更安全 |

## 三、本轮落地

1. **`core/cdc_chunk.py`：CDC 全局块库**（纯 Python，零外部依赖）
   - Gear 滚动哈希（隐式 64 字节窗口）→ 变长块（min 2K / avg 8K / max 64K）；
   - `ChunkStore`：内容寻址块库（`chunks/<ab>/<sha256>`）+ 块引用（refs）+
     统计（逻辑/物理/去重率）；
   - `rebuild_file` 逐块 sha256 校验后原子落盘，块损坏立即暴露。
2. **元数据保真**（`core/dedup_source.py` 清单 v2）：
   - 文件补 **uid/gid + inode + 链接数**；目录补 **mtime/mode/uid/gid**；
   - **空目录**进清单（此前从文件路径推导 → 空目录丢失）；
   - 符号链接补自身 mtime/mode/uid/gid；
   - **硬链接**：同 inode 只留一份内容 + `LNKTYPE` 硬链接条目（恢复后同 inode）。
3. **修复 2 个真缺陷**：
   - `lstrip("./")` 把隐藏文件前导点吃掉（`'./.hidden.txt'`→`'hidden.txt'`）→
     远端路径还原错、SFTP 拉取 ENOENT、恢复后文件名少一个点。全仓 5 处统一
     改为「只剥一次 `./` 前缀」（新增 `dedup_source.rel_key`，回归单测锁定）。
   - 硬链接在清单重建通道被当成两个普通文件（恢复后 inode 不同）→ 已修（见上）。

## 五、第二轮开发（同日完成）：传输级 CDC + 稀疏保真

### 5.1 传输级 CDC（大文件内部变化只传变化块）✅ 已接入主链路

按「零安装」约束实现（与 xtrabackup 推送同构）：

- 平台**临时推送** python3 分块脚本到远端 `/tmp/aidbm_cdc_*.py` 执行 →
  输出块清单（`offset/size/sha256` + 整文件指纹），**finally 删除**（零安装、零残留）；
- 远端脚本与平台 `iter_chunks` **同一套边界算法**（同一 GEAR 表 / MASK / min-max），
  单测逐块比对锁定——否则块库命中率归零；
- 平台只拉「块库缺失」的块（SFTP seek+read）→ 重组 → 整文件 sha256 硬校验；
- 远端无 python3 → 自动回退整文件 SFTP（正确性不受影响）；
- 接入 `pull_files_dedup` 的大文件分支（≥4MB），失败自动回退。

**实测（20MB 文件改中间 512KB）**：

| 轮次 | 逻辑量 | 实传 | 块级明细 |
|------|--------|------|----------|
| 首轮（建块库） | 20.0 MB | 20.0 MB | 全量 |
| 次轮（改 512KB） | 20.0 MB | **524.6 KB（节省 97.4%）** | 总 1551 块，**命中 1504 / 仅拉 47** |

### 5.2 稀疏文件 `--sparse` ✅ 已接入

- **备份侧**：远端打包命令加 `tar --sparse`（稀疏洞不被展开成实占）；
  远端 tar 不认识 `--sparse`（BusyBox/老版本）时**自动去掉重试**并记录该主机。
- **恢复侧**：优先系统 tar 解包（GNU tar 还原稀疏洞）→ 失败回退 Python tarfile；
  远端恢复本就走 `tar -xzf`（自动保稀疏）。
- **实测**：10MB 稀疏文件（3 段数据）→ 归档仅 **200 B** → 恢复后大小 10MB、
  sha256 一致、**稀疏语义保持**（实占 135KB ≪ 10MB）。
- 去重清单重建通道（Python tarfile 写盘）对稀疏按实占展开（内容/大小一致），
  如实标注；主路径（标准通道）已全保真。

## 六、诚实边界与下一步

- **CDC 已接入主链路的大文件传输**（≥4MB 走块级，实测 97.4% 节省）；小文件仍
  走文件级去重（`.dedup_store/files/<sha>`，实测 83.3% 节省）。
- **下一步**：① 块库作为存储层（同一内容段跨文件/跨任务只存一份，替代文件级
  库的整文件副本）；② CDC 与增量通道（`_incremental_transfer`）融合——当前
  增量是文件级（变化文件整拉），可同样按块拉；③ 稀疏在去重重建通道的打洞支持。
- **zbackup 的"去重后无冗余"风险**我们不引入：产物仍是标准 tar，块库是加速层，
  不改变恢复链与多副本语义。
- **Windows 主机**：文件实时同步（指纹轮询）仍只支持 Linux（find+sha256sum），
  Windows 走「文件备份」通道（PowerShell 指纹清单，已支持全量/增量）。
