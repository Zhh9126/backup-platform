## 二、本轮（2026-11-14）新增能力与真机实证

### 2.1 备份并行预算（平台并发 × 单任务引擎并行）

新增 `core/parallel_plan.py`：统一两层并行口径，**平台并发被压小时由单任务内部并行补足**，避免批量/组合任务成员长时间排队导致 drift。

| 项 | 说明 |
|---|---|
| 预算公式 | `总并行预算（默认 8，AIDBM_BACKUP_PARALLEL_TARGET 可调，0=关） ÷ 平台并发上限` |
| 优先级 | 任务 `extra_options.engine_parallel`（0=强制串行）> 保护策略并行度上限（core 4 / important 2 / general 1）> 自动推算 > 硬上限 8 |
| 引擎落地 | MySQL 物理：XtraBackup/mariabackup `--parallel=N`（本机 + 远端）；PG/金仓/openGauss：`pg_dump -j N`（非目录格式自动切 `-Fd` 并打包单文件 `.dir.tar.gz`，恢复侧自动建库）；全实例逻辑备份：逐库并发 dump，manifest 记 `parallel_dump` |
| 可观测 | 记录消息追加 `[排队等待 Xs（平台并发上限 N 路）· 并行预算：引擎并行 N 路 · 来源]`；操作日志含「并行模式 / 排队等待」；`GET /api/system/concurrency` 返回 `engine_parallel` 快照 |
| 真机实证 | MySQL 5.7 物理 `--parallel=4` 成功 99.5MB/2.1s；PG `-Fd + -j 4` 产物含 toc.dat 且异名库恢复三行中文一致；PG 全实例 `parallel_dump=4`；并发上限压到 1 时第二个任务如实记录"排队等待 2.2s"（两任务均成功） |

**本轮修复的 11 个部署缺陷（均为真机暴露）**

1. 同机已有 `mysqld/mongod` 进程即拒绝部署 → 改为「目标端口占用 + 目标数据目录非空」双重防误删，支持多实例；
2. 部署覆盖 `/etc/my.cnf`（全机共享）→ 改为实例级 `{base_dir}/my.cnf`，启动强制 `--defaults-file`；
3. `socket=/tmp/mysql.sock` 与同机实例抢占 → 改为 `{data_dir}/mysql.sock` / `mysqlx.sock`；
4. `mysql`/`psql`/`ksql` 命令未带 `--defaults-file`/`-p`/`-P` → 会把授权/改密语句打到同机**现网实例**上（PG 分支实测命中），已全部显式指定；
5. `/root/.my.cnf` 无条件覆盖 → 仅在「此前不存在且本机仅本实例」时写入；
6. `/etc/profile.d/*.sh`、`/usr/local/bin/redis-start.sh` 无条件覆盖 → 改为实例级 `env.sh`/`start.sh`，全局文件仅首次生成；
7. 金仓 `initdb --mode=pg` 参数不存在（V9R3 只认 `-m/--dbmode` 且仅支持 MySQL 兼容模式）→ 探测后按版本传参；`ksql` 缺 `-U SYSTEM -d test` 导致"角色 kingbase 不存在"、改密失败；
8. 金仓缺 `license.dat` 启动直接 FATAL、`sys_ctl` 启动失败仍打印 `DEPLOY_OK`（假成功）、Redis 就绪探测未带 `-p` 连到别实例、部署包暂存 `/tmp`（Kylin 上 `/tmp` 是 tmpfs，1.5G 包写爆内存）→ 全部修掉：license 预检、启动后端口校验、探测带端口、暂存改 `/var/tmp`；
9. **MySQL X Plugin 端口抢占**：X 端口默认取主端口+1，同机连续端口部署时 23306 实例的 X=23307 直接把 23307 实例的主端口占了（表现为"23307 部署失败但 23307 在监听"）→ X Protocol 改为**默认关闭**（`mysqlx=OFF`），需要时 `config_json.mysqlx=1`（端口=主端口+10000）；
10. **部署执行没有超时看门狗**：远端脚本卡死（低内存 OOM / 解压异常）时平台一直显示「运行中」（171 实测卡死 5 分钟以上、无任何输出，最后需人工介入）→ 增加总超时（默认 3600s）+ 静默超时（900s）+ SSH 会话存活检查；本机执行分支同样加超时（原来死等 stdout）；
11. **部署前置没有内存预检**：可用内存不足时 MySQL 初始化被 OOM 杀掉，用户只看到"卡住" → 增加按 `buffer_pool + 128MB` 估算的内存预检（不足直接拒绝、偏紧给出警告与调参建议）。

> 未验证：Oracle / 达梦 / openGauss 三类**缺安装介质**（171 无包、168/129 离线、170 只有已安装目录无安装器），本轮未做部署验证；Oracle 部署本身仅完成介质解压 + 环境变量（不建实例），已在脚本与日志中显式标注边界。

### 2.4 多通道并行拉回 · 限速链路实测（2026-11-15）

数据：171 上 4 × 50MB 真实文件（共 200MB），走 `sftp_pull_files_parallel`（每通道独立 SSH 连接、单片自带断点续传、限速按通道均分）。

| 限速 | 通道数 | 耗时 | 吞吐 |
|---|---|---|---|
| 不限 | 1 | 131.02s | 1.5 MB/s |
| 不限 | 4 | 34.93s | 5.7 MB/s（**3.8×**） |
| 10 MB/s | 1 | 130.35s | 1.5 MB/s |
| 10 MB/s | 4 | 41.80s | 4.8 MB/s（**3.1×**） |
| 2 MB/s | 1 | 185.42s | 1.1 MB/s |
| 2 MB/s | 4 | 123.64s | 1.6 MB/s（**1.5×**） |

**结论（实测口径）**：① 单连接 SFTP 在内网只有 ~1.5 MB/s（协议往返 + 加密开销），**多通道是提升大文件拉回速度的主因**；② 限速高于单连接能力时（10MB/s）多通道收益几乎不打折（3.1×）；③ 限速成为总带宽瓶颈时（2MB/s）收益收窄到 1.5×，但仍优于单通道；④ 6 组数据 sha256 全部一致。

### 2.5 金仓 PITR 真机闭环（171 / KingbaseES V9R003C011）

| 步骤 | 实测结果 |
|---|---|
| 归档 | `archive_mode=always` + 真实 `archive_command`（原为 `exit 0` 假归档）→ reload 后 `sys_switch_wal()`，**16MB WAL 段真实落盘**（含 `.backup` 标记） |
| 基础备份 | `sys_basebackup -Fp -X fetch` → 408MB（`backup_label` + `base` + `global`…） |
| 时间点 | A 阶段写 3 行 → T1=`2026-11-15 00:40:00`；B 阶段再写 2 行 → T2=`00:40:10` |
| 恢复 | 还原到独立目录 + `recovery.signal` + `restore_command='cp arch/%f %p'` + `recovery_target_time=T1` + 端口 54324 → 启动并 promote |
| 校验 | 恢复实例内 `count(*)=3`，**B 阶段 2 行不存在**（时间点回放生效） |
| 收尾 | 停恢复实例、删目录、`archive_command` 还原为 `exit 0` 并 reload；磁盘/内存回归基线 |

> 平台侧现状（如实）：`core/rt_backup/pitr.py` 对 kingbase 仍走"已捕获、暂不支持自动回放"分支（`_T06_CDC_ENGINES`）。本轮证明**命令序列与金仓能力可行**，把该序列自动化为平台 PITR 通道是下一步（尚未接入）。注：金仓 V9 把 `||` 当逻辑 OR，校验 SQL 需用 `string_agg(col, ',')` 而非字符串拼接。

| 备份前坏块检测 | MySQL CHECK TABLE；Oracle fast（视图级）/ full（RMAN VALIDATE CHECK LOGICAL）；corrupt 阻断备份，failed 如实区分 |
| Oracle 非归档热备 | `BEGIN/END BACKUP` 文件热拷（免开归档、免 RMAN），失败兜底 END BACKUP 防悬挂 |
| 自定义脚本 | 全库型通用，平台注入 `PLATFORM_*` 环境变量，产物 SFTP 拉回并算 sha256 |
| 存储 | 三级（L1 MinIO / L2 S3 / L3 本地导出）、生命周期下沉、全局重删、存储池加密（AES-256-GCM / SM4）、磁带库/可移动介质（工程化接入，见边界） |
| 插件市场 | 服务端插件化（XtraBackup / MariaDB Backup / pgBackRest / MongoDB Tools 等），内置包标记 + 离线包安装 |

## 八、安全与合规

- **不可变备份四层**：保留锁定 → 写保护 → 完整性复检 → 删除四路拦截（应用层；物理不可变需 FS/S3 Object Lock，不支持时显式报告）。
- **加密**：凭据与产物 AES-256-GCM 信封加密；支持 **SM4**（国密）；密钥来源：环境变量 / 系统设置托管 / 外部 KMS。
- **高危操作防护**：恢复 / 清理 / 删除 / 主机删除需一次性验证码（4 位、5 分钟、校验即销毁防重放）；主机「受保护」标记对恢复到该主机的入口硬闸拦截。
- **三员管理**：RBAC 24 权限点 × 3 内置角色（admin/operator/viewer），菜单按权限收敛 + API 二次校验；口令脱敏与审计日志。
- **安全审计**：SQL 注入/路径穿越/SSRF/RCE 类问题已做全站整改（v2.3.7–v2.4.0 期间）；操作日志 + 审计日志双通道。

## 十四、诚实边界（不承诺清单）

1. **未做真机验证的部署类型**：Oracle、达梦、openGauss 仍未验证——介质现状：170 只有**已安装目录**（`/dm8`、Oracle home）没有安装器（达梦部署需 `DMInstall.bin`），171 无包，168/129 离线，openGauss 两台机均无介质；Oracle 部署脚本本身只做介质解压 + 环境变量，**不创建实例**（需 `runInstaller` + `dbca`，脚本内已打印命令）。待介质到位即可直接跑（脚本与用例已就绪）。
2. **磁带库**：工程化接入（池类型 `tape`、存储后端、路径/介质抽象）已完成，但**无真实磁带库/机械手/多驱动器真机验证报告**。
3. **PITR 覆盖不均**：MySQL（binlog 多段回放）、PG（WAL）、Oracle LogMiner 已闭环；**金仓 PITR 于 2026-11-15 在 171 真机闭环**（归档→basebackup→恢复到 T1→B 阶段数据不存在），但**平台自动回放通道尚未接入**（当前如实拒绝并提示手工前滚）；**达梦 dmrman PITR 仍仅生成恢复脚本，未做真机时间点回放**。
4. **SQL Server** 无 CDC 实时通道；表级恢复需自建脚本（T-SQL 无单表备份）。
5. **实时链路的仿真降级**：仅 `DEMO_MODE` / `demo_only` / `rt_mode=sample` 三种显式演示场景允许；能力不足（引擎未注册/依赖缺失）一律 FAILED，不产假数据。
6. **不可变备份是应用层防护**：防平台自身误删与凭据泄露；root 级强删、物理介质不可变需文件系统/S3 Object Lock 配合。
7. **恢复点安全检测是启发式**，不做病毒查杀（离线无病毒库），结论用 `suspect/clean/unknown` 三态并标注。
8. **多租户 / SNMP / 监控大屏**：未实现（不在当前路线）。
9. **镜像并发收益**：并行度上限 8；收益受源库 IO/CPU 与链路带宽限制，超配只增加争用。
10. **群晖 DSM** 已有文件备份通道，但无真机验证报告。
