## 一、数据库 OS 用户标准变量（环境差异变量化）

**背景**：客户环境里数据库软件的安装属主用户可能与默认不同（Oracle 不叫 `oracle`、达梦不叫 `dmdba`、openGauss 不叫 `omm`）。此前 `su - oracle`、`su - dmdba` 等写死在各引擎中，环境不匹配即整链路失效。

**设计**：流程保持标准不变，把「在哪个 OS 用户下执行」收敛为标准变量，三级覆盖链：

```
任务 extra_options.db_os_user  >  纳管主机 ssh_hosts.db_os_user  >  库型默认
```

- 库型默认表：oracle→oracle、dameng→dmdba、opengauss/panwei→omm、kingbase→kingbase、postgresql→postgres、mysql/mariadb→mysql
- 数据模型：`ssh_hosts` 新增 `db_os_user` 列（建表 + 存量库自动迁移）
- 落地范围：`base._resolve_check_user()` 统一入口；Oracle 9 处、达梦全部写死点（su/chown/home 路径/6 处 check_user）、openGauss 3 处、跨主机恢复脚本、Oracle schema 克隆全部接入
- 前端：主机纳管表单与备份任务高级选项各新增「数据库 OS 用户」输入框，编辑回显
- 验证：`tests/test_db_os_user.py` 12 条（优先级链 / JSON extra 兼容 / 主机字段落库往返 / 引擎集成 / 禁止回退写死的静态契约）

**使用**：某台服务器安装用户非默认 → 纳管主机填一次全局生效；单任务临时差异 → 任务高级选项覆盖；不填则完全兼容旧行为。

## 二、四库型备份恢复深度 E2E（源码 30/30）与三个工具解析修复

走生产同款入口（`run_task_now` / `run_restore_now`），恢复后用原生驱动直查目标库行数与中文内容硬核对，不采信平台状态。环境：MySQL 3307 / PG 14.12@5785 / 达梦 DM8@137:5236 / 金仓 V9R3@137:54321（137 当日复活）。

| 库型 | 逻辑备份 | 深度校验 | 恢复+硬核对 | 物理备份 |
|---|---|---|---|---|
| MySQL 3307 | mysqldump ✓ | dump header ✓ | ✓ 行数/中文一致 | XtraBackup ✓ |
| MySQL 全实例 | 9 库 tar ✓ | manifest 逐库 ✓ | — | — |
| PG 5785 | pg_dump ✓ | header ✓ | ✓ | pg_basebackup ✓ |
| 达梦 137 | dexp ✓ | ✓ | ✓ dimp 导回 | disql 联机备份集 ✓ |
| 金仓 137 | sys_dump ✓ | ✓ | ✓ sys_restore 导新库 | sys_basebackup ✓ |

首轮 20/28，暴露并修复 3 个工具解析缺陷：

1. **本机物理备份预检误报**：`_ensure_local_clients_on_path` 的兜底 glob 只扫 `/opt` 两级，漏掉 `/pgdb/pgsql/bin` 等自定义根目录——`pg_basebackup` 明明在却报「缺少客户端工具」。修复：终极兜底接入 `_resolve_local_tool`（宽目录枚举 + `--version` 版本择优）。
2. **金仓远端预检必挂**：`remote_has_tool` 带 `check_user` 时只做一次 `su - <user> -c command -v`，失败即判缺失、不落 find/glob 兜底。137 实况是 kingbase 用户 profile 没配 PATH（工具实际在 `KESRealPro/<版本>/Server/bin`）。修复：失败后复用 `resolve_remote_tool` 完整三级解析（进程定位 → glob 枚举 → find，含缓存）。
3. **达梦恢复 rc=127**：`_restore_logical_remote` 解析出了 `dimp_bin` 绝对路径却硬编码裸 `dimp`（root 登录 shell 无 dimp）。修复：使用解析值。

防回退：`tests/test_tool_resolution_fix.py` 4 条（含本机实况回归）。

## 三、达梦 dimp 恢复语义：存量表覆盖（TABLE_EXISTS_ACTION=REPLACE）

**现象**：目标 schema 存在与备份同名表时，dimp 默认整表 fail（rc=2），137 SYSDBA 存量测试表触发。

**修复**：远程 dimp / 本机 dimp / cross_host DM 恢复脚本三处统一加 `TABLE_EXISTS_ACTION=REPLACE`（与 Oracle impdp 语义对齐）。

**实测教训（重要）**：**不能加 `IGNORE=Y`**——它让 dimp 在表已存在时跳过重建直接插数据，触发 `-6602` 唯一约束冲突，与 REPLACE 语义互斥。加 IGNORE=Y 后 rc=2，去掉后 23 张表全部导入成功。已写入代码注释与静态契约（测试禁止回加）。

## 四、自定义脚本通道实测（13/13）

`backup_mode=custom` 的自定义备份/恢复脚本能力全链路实测，通道零改动通过：

- **本机通道**（MySQL 同机）：mysqldump 真实导出、多文件产物扫描拉回（sql + env.marker + manifest）、真实 sha256；恢复脚本用 `$PLATFORM_BACKUP_FILE` 灌入 `$PLATFORM_RESTORE_DB`，硬核对 5 行中文一致
- **SSH 通道**（137 达梦）：脚本 SFTP 上传、disql spool 真实导出拉回、恢复时备份文件自动推送远端、远端标记文件回查证明真实执行
- **环境变量注入完整性**：`scope=single_table`、`tables=t1`、`pw_set=yes`、`PLATFORM_DB_NAME/PORT` 逐项验证
- **失败如实**：脚本 `exit 3` → 任务 failed 且带 rc 与脚本输出；不写产物 → 明确报「请把产物写入 $PLATFORM_BACKUP_DIR」
- 达梦脚本密码含 `@` 的可用写法：`disql "SYSDBA/\"$PLATFORM_DB_PASSWORD\"@host:port"`
