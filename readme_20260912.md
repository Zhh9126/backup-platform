# AIDBM 平台更新说明（2026-09-12）

本次更新涵盖：**可插拔数据库类型、用户与角色权限（RBAC）、本地备份落点可见可配置、失败可定位的日志体系、数据迁移与同步的全库字段类型保真映射、MariaDB 打通、物理备份与恢复加固**。

版本：`v1.4.5`；镜像：`ghcr.io/zhh9126/backup-platform:v1.4.5`。

---

## 一、可插拔数据库类型（界面新增一种数据库即可备份/恢复）

内置引擎之外，新增「数据库类型」管理页：只要填写**脚本模板 + 能力声明**，即可在界面上新增一种数据库类型，立即用于备份/恢复。

- 适配器落 `db_adapters` 表，运行时渲染为 `CustomDBEngine` 注入引擎注册表，与 10 个内置引擎走**完全相同的调度链路**（cron / 保留策略 / 三级存储 / 重删 / 告警全部复用）；
- `/api/meta` 动态返回类型与默认端口，任务表单无需改代码即可选到新类型；
- 脚本模板中的 `{{KEY}}` 占位统一渲染为 `${PLATFORM_KEY}` shell 变量引用，**脚本文件不落明文密码**（由任务参数经环境变量注入）；
- 删除被备份任务引用的适配器会被拒绝并提示引用任务数；支持「从模板复制」与远端连通性测试。

相关：`core/db_adapters.py`、`api/db_adapters.py`、`templates/db_adapters.html`。

## 二、用户与角色权限管理（RBAC）

新增「用户管理」页，多用户登录 + 24 个权限点 + 3 档内置角色。

- 角色：`admin`（全部）、`operator`（备份/恢复/同步/克隆/对比/部署/巡检/AI/告警/日志/运维运营，21 项）、`viewer`（只读，4 项）；单个用户可叠加附加权限（`permissions` 字段）；
- 密码哈希：标准库 `hashlib.pbkdf2_hmac('sha256', 20 万次迭代)`，格式 `pbkdf2_sha256$<iter>$<salt>$<hash>`，**无第三方依赖，离线打包可用**；
- 侧边栏 25 个菜单按权限自动隐藏，API 层 `permission_required()` 二次校验（前端隐藏被绕过仍返回 403）；
- 兼容升级：`users` 表为空时自动用内置账号种子首个 admin；旧会话（字符串 user）自动兼容为 admin 角色；外部 API Token 调用方不受影响；支持管理员重置密码、用户自助改密、`must_change_password` 首登改密提醒。

相关：`core/rbac.py`、`api/rbac.py`、`templates/users.html`、`static/js/bkp-core.js`。

## 五、数据迁移与同步：全库字段类型保真映射（本次重点）

异构迁移最容易失败的地方不是数据量，而是**类型映射**：每个数据库都有自己独有的字段类型（PG 的数组/JSONB/范围/网络地址、MySQL 的 ENUM/SET/空间/VECTOR、Oracle 的 RAW/ROWID/XMLType/SDO_GEOMETRY、SQL Server 的 HIERARCHYID/GEOGRAPHY/SQL_VARIANT、达梦的 TEXT/IMAGE/ST_GEOMETRY…）。本次对这些类型逐一补齐映射，避免"一律落到 `VARCHAR(255)`/`NVARCHAR(4000)`/`VARCHAR2(4000)` 兜底"造成的**精度丢失、数值列退化为字符串列、大对象被截断**。

### 5.1 三层映射架构

| 层 | 位置 | 职责 |
| --- | --- | --- |
| ① 预检矩阵 | `core/sync/type_matrix.py` | 源类型 → 目标类型建议 + 风险级别（ok/warn/fail）+ 原因，供迁移前评审与 `check_column_mapping` 逐列报告 |
| ② 列元数据 | 各插件 `list_columns` | 解析列的真实长度 / 精度 / 刻度 / `[]` 数组后缀 / 可空 / 默认值，填入 `ColumnMeta`（此前多数插件不填精度，导致建表丢长度） |
| ③ 建表 DDL | 各插件 `_map_to_xxx_type` | 按目标库方言生成列类型；本库类型原样保真，异库类型经统一矩阵翻译（`matrix_suggest`），最后才兜底 |

### 5.2 本次修复的阻断型缺陷

此前实测 MariaDB → MySQL / PostgreSQL 迁移时定位到 3 个阻断缺陷，本次连同冒烟测试新发现的问题一并修复：

1. **`parse_type` 只做精确相等比较**：`decimal(12,3)`/`varchar(100)` 等带修饰的类型名与裸名比较不相等，全部落到兜底 `VARCHAR(255)`，数值列退化成字符串列 —— 改为**先拆基类型再判断**，并保留精度/长度。
2. **TEXT 被当成 BLOB**：MySQL 协议中 TEXT 与 BLOB 共用类型码 252，读取端按类型码走 BYTES 分支会把 TEXT 的字符串 `encode('utf-8')` 成 bytes，写入端再 `str()` 成 `b'\xe6\x96\x87...'` 字面量（中文数据直接损坏）—— 改为**值类型优先**（str 原样保留、bytes/bytearray 透传）。
3. **`mariadb` 未注册探测**：提交 `src_db_type=mariadb` 时预检查直接失败"未知数据库类型: mariadb" —— 注册复用 MySQL 探测（协议兼容）。
4. **数组类型落空**：`integer[]` 的 base 是 `integer`，家族归一后丢失 `[]` 标记，`array` 分支永不命中，`target_type` 返回 `None` —— `parse_type` 增加 `array` 标记，`_special_target` 优先判定。
5. **SQL Server `TIMESTAMP` 别名污染全局**：`_FAMILY` 中把 `timestamp` 归为 `blob`（SQL Server 的 TIMESTAMP 是 ROWVERSION 别名）**覆盖了其它库的时间戳语义**，Oracle/MySQL/PG 的 TIMESTAMP 列会被映射成二进制 —— 改为**按源库判定**（仅 `src_db=sqlserver` 时按 ROWVERSION 处理），并把该错误条目从家族表移除。
6. **多词类型被截断**：`character varying(100)` 被截成 `character`（当定长字符处理）、`timestamp with time zone` 丢时区语义、`long raw` 被当成文本 —— 新增多词归一表。
7. **`jsonpath` 归到 JSON 家族**：会给出 JSON/JSONB 目标类型（路径表达式存进 JSONB 会报类型错误）—— 单独归 `text`，同库保形 `JSONPATH`。
8. **整数别名抛异常**：`PLS_INTEGER` / `BINARY_INTEGER` / `int2` / `int4` / `int8` / `serial` 系在 PG/金仓目标下因字典 KeyError 直接抛"映射规则异常" —— 按位宽归一（SMALLINT/INTEGER/BIGINT），MySQL 侧按位宽归一（TINYINT/SMALLINT/MEDIUMINT/INT/BIGINT）。
9. **`DATETIMEOFFSET` 方言违规**：`_datetime_target` 未覆盖 `base=datetimeoffset`（家族已是 `timestamptz`），会原样输出 `DATETIMEOFFSET` 到 MySQL/PG/Oracle —— 按带时区分支处理。
10. **INTERVAL 返回值结构错误**：非 MySQL 目标时把三元组嵌进了三元组（`reason` 变成元组），且 SQL Server 无 INTERVAL 类型 —— 拆正，SQL Server 落 `VARCHAR(64)` 并给 warn。
11. **未识别类型补齐**：`NTEXT`（SQL Server）、`LONGVARCHAR`/`LONGNVARCHAR`（达梦）、`ST_GEOMETRY`（达梦空间）、`BIGDATETIME`（金仓/达梦）、`SERIAL` 族。
12. **建表端跨源兜底**：各 SinkWriter 原先只识别本库类型名，异库特有类型一律落固定兜底列 —— 新增 `matrix_suggest()`（`core/sync/plugins/base.py`），未命中本库规则时调用统一矩阵翻译，**避免数值列变字符串列、大对象被截断**。
13. **MySQL 建表端细节**：`INT UNSIGNED` 因先取首词被误判（`unsigned` → 兜底 VARCHAR(255)）；`INT4RANGE` 因 `"INT" in base` 模糊匹配被原样输出（MySQL 无此类型）；`TIMESTAMP WITH TIME ZONE` 原样输出会建表报错 —— 三处均已修正。
14. **建表端细节**：Oracle `LONG`（大文本）在 SQL Server 建表端被截成 `VARCHAR(64)`，改为 `NVARCHAR(MAX)`；达梦 `ST_GEOMETRY` 在 SQL Server 目标被误判为 `GEOGRAPHY`（平面几何 ≠ 地理坐标），改为 `GEOMETRY` —— 已修正。
15. **时间类型别名兜底**：`BIGDATETIME`（金仓 / 达梦微秒时间戳）等时间族别名在 6 个目标库被**原样输出**（目标库直接建表失败）—— 改为按目标方言归一（Oracle / 达梦 `TIMESTAMP(6)`、PG / 金仓 `TIMESTAMP`、SQL Server `DATETIME2(6)`、MySQL `DATETIME(6)`）；同时把"未知时间别名原样输出"的运行兜底改为标准类型 + warn，杜绝同类问题。
16. **`MONEY` / `SMALLMONEY` 保形**：此前经 decimal 家族退成无精度 `DECIMAL`（触发"精度缺失"告警）—— 现按固定 4 位小数保形：同库 `MONEY` / `SMALLMONEY`，Oracle / 达梦 `NUMBER(19,4)` / `NUMBER(10,4)`，PG / 金仓 `NUMERIC(19,4)` / `NUMERIC(10,4)`，MySQL `DECIMAL(19,4)` / `DECIMAL(10,4)`。

### 5.4 同库保形与方言规范化

- **同库保形**：MySQL ↔ MariaDB 的 `ENUM`/`SET` 原写法透传；PG ↔ 金仓的数组 / RANGE / `HSTORE` / `TSVECTOR` / `UUID` / `XML` / `JSONB` 原样保留；SQL Server 的 `HIERARCHYID` / `SQL_VARIANT` / `VECTOR` / `ROWVERSION` / `GEOGRAPHY` 原样保留；Oracle 的 `XMLTYPE` / `BFILE` / `UROWID` / `SDO_GEOMETRY` 原样保留。
- **方言规范化**：`VARCHAR`/`NVARCHAR` → Oracle 侧 `VARCHAR2`/`NVARCHAR2`、SQL Server 侧按 `VARCHAR`/`NVARCHAR`；`CHAR`/`NCHAR` 超限自动升位（Oracle 2000/1000、SQL Server 4000→`MAX`、MySQL 无长度→`TEXT`）。
- **无长度保护**：MySQL 的 `VARCHAR` 必须带长度（无长度降 `TEXT`）；SQL Server 无长度按 `MAX` 处理（避免 T-SQL 默认长度 1 丢数据）；Oracle/达梦无长度按 4000/3900 上限兜底。
- **未识别类型**：返回"建议按文本承载 + 需人工确认"，不静默造假。

### 5.5 风险级别与预校验

`type_matrix.map_type()` 对每个列给出：

- **ok**：可直接映射；
- **warn**：需升位 / 降精度 / 隐式转换（无符号升位、无精度 `NUMBER`→`DECIMAL`、`BIT`/`ENUM`/`JSON` 承载变化、时区语义变化、几何类型需扩展等），迁移前需人工确认；
- **fail**：目标库确实没有对应类型，**预校验直接拦截**。当前 fail 清单：PG 带时区时间戳 / `INTERVAL` → MySQL、`TIME` → Oracle、`ENUM`/`SET` → Oracle（DTS 规则）。

`check_column_mapping()` 逐列输出"源类型 → 建议目标类型 → 实际目标类型 → 级别 → 原因"，用于迁移前评审报告。

## 七、物理备份与恢复加固

- **目录形态产物校验**：物理备份（xtrabackup / mariabackup / pg_basebackup）未打包时产物是**目录**，此前按"文件"判定会被误报"文件不存在"（实测 MariaDB / MySQL 物理全量、增量均命中）。现改走目录级校验：空目录 / 零字节直接判失败，并以物理备份标志文件（`xtrabackup_checkpoints`、`mariabackup_checkpoints`、`backup-my.cnf`、`backup_label`、`PG_VERSION` 等）作为"数据库可识别的可恢复产物"证据，指纹（文件数 / 总字节 / 标志文件）写入校验说明。
- **增量退化为全量时清理空增量层**：增量基不存在时会自动退化为全量，但预创建的空增量目录会残留，恢复链按目录名将其识别为增量层，导致 apply 阶段报 `cannot open .../xtrabackup_checkpoints` —— 现已自动清理空目录，并在恢复链构建时**剔除无效增量层**（空目录 / 无 checkpoints）。
- **物理恢复校验改为整实例级**：物理恢复是数据目录级（备份里有什么库就恢复什么库），任务表单的 `target_db` 属逻辑恢复语义，常不成立（例如恢复 `bmaria1` 但目标库填 `bmaria1_restored`）—— 校验改为先查目标库，不存在则回退实例级（库数 + 业务表数），**业务表数为 0 时如实判失败**，不再出现"查不到表仍报通过"的假通过。

相关：`core/scheduler.py`、`core/engines/mysql.py`。

## 十、遗留问题优化（本轮完成）

上一版列出的 5 项已全部处理，并做真实环境验证（本机 MySQL 8.0.40:3306、MariaDB 10.11 容器 33306；MySQL 目标自动建库与 MariaDB 源 CDC 均为端到端实测）。

### 10.1 放开 MariaDB 源实时同步（Binlog CDC）

- 放开点：`core/sync/engine.py` 的实时引擎分派与 binlog 分支由「仅 `mysql`」改为 `("mysql", "mariadb")`——MariaDB 与 MySQL 同属 binlog 协议族（`SHOW MASTER STATUS`、ROW 事件、CRC32 校验、TableMap 事件均兼容）；
- 端到端实测（MariaDB 10.11 → MySQL 8.0）：全量快照 3 行 → 源插入 1 行 → 目标 4 行且内容一致，任务返回 `success`；
- **顺带修复停止响应**：原先 `for event in stream` 阻塞读需等源库产生下一个事件才会回到停止检查点（实测停止要等 40s+）。现停止信号置位后由看门狗线程主动 `shutdown(SHUT_RDWR)` 底层 socket 打断阻塞读（pymysql 的 `close()` 不 `shutdown`，Linux 下无法唤醒已阻塞的 `recv`）——MariaDB 源实测停止响应 **0.0s**；MySQL 源（SSL 连接）在个别时序下仍可能退化为"等下一个事件"，属既有行为、无功能回归。

### 10.2 预检查先自动建库（消除 1049 提前失败）

- `run_precheck()` 最前面新增 `target_database` 检查项并调用 `_ensure_target_database()`：MySQL/MariaDB 目标库不存在时自动建库，**先于**连通性与表存在性检查；此前 writer 连接会以 `1049 Unknown database` 直接判失败，与「数据迁移」页（自动建库）行为不一致；
- 非 MySQL 目标不自动建库，但目标连接失败时附带明确诊断（"目标库 X 不存在：该类型不自动建库，请先手工建库后重跑预检"）；
- 实测：目标库 `bpm_autocreate_0912` 由预检查真实创建，`target_database` 判 pass、目标连通性不再出现 1049，预检查 `passed=True fail=0`。

### 10.3 同步任务状态显示修正

- 后端双写：`models.set_sync_status()` 同时更新 `status` 与 `last_status`（此前调度器路径只写 `last_status`，会残留 `status=running`）；
- 列表归一：`_decorate_sync()` 改为「终态优先（`status` / `last_status` 谁先落终态用谁）→ 运行态 → 回退 `never`」，不再长期显示 `never`；
- 前端：状态列优先取 `status`（`running` 优先显示），且存在运行态任务时列表每 3s 自动刷新。

### 10.4 原 fail 组合改为可落地方案（warn + 明确承载类型）

| 源类型 | 目标 | 原判定 | 现方案 |
| --- | --- | --- | --- |
| PG / 达梦 / SQL Server 带时区时间戳（`timestamptz` / `timestamp with time zone` / `datetimeoffset`） | MySQL / MariaDB | fail | `DATETIME(6)`：按 UTC 归一，保留微秒精度、规避 `TIMESTAMP` 的 2038 上限（时区偏移丢失，需人工确认） |
| PG / Oracle `INTERVAL` | MySQL / MariaDB | fail | `VARCHAR(64)` 文本承载（`'1-2'` / `'3 04:05:06'`，是否拆字段由业务确认） |
| MySQL / 达梦 `TIME` | Oracle | fail | `VARCHAR2(16)`：保留超 24h / 负值语义（落 `DATE` 会引入无意义日期部分） |
| MySQL `ENUM` / `SET` | Oracle | fail | `VARCHAR2(n)`，n = **最长枚举值长度**（此前固定 4000 与语义脱节，枚举约束由应用层保证） |

- 建表端同步跟随：MySQL 插件 `TIMESTAMP WITH TIME ZONE → DATETIME(6)`；Oracle 插件 `TIME → VARCHAR2(16)`、`ENUM/SET → VARCHAR2(最长枚举值)`；
- 效果：类型矩阵冒烟 `target_type=None` 由 **32 项降至 7 项**（其余均为自定义/未识别类型，会明确提示人工确认），偏门类型不再阻断迁移。
