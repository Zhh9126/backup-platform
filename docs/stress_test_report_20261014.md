# 2026-10-14 并发与大数据量压测报告

> 环境：单机 2C / 4.7G 内存 / 37G 盘（源码运行，进程内注入）；MySQL 5.7.44@3307
> 与 2026-09-15 基线（v1.4.6，1200 任务/并发 150，QPS 81.8）同源方法，本轮聚焦**单库大数据量**与**并发备份/并发读写**两个维度。

## 一、阶段 A：大数据量（100 万行 / 228MB dump）

| 项 | 结果 |
|---|---|
| 源库 | stress_big：4 表 × 250000 行 = **1,000,000 行**，随机填充（每行 ~200B 唯一数据） |
| 全量备份 | ✅ 成功，**36.5s**，产物 **35MB**（zstd 6.5:1） |
| 恢复 | ✅ 成功，**7.5s**（目标库 stress_big_r1） |
| 硬核对 | ✅ 恢复库 big1 = 250000 行（与源一致；4 表合计 100 万行） |
| 说明 | mysqldump 流式落盘（内存与产物大小无关）；备份期间平台 RSS 平稳 |

## 二、阶段 B：并发备份（10 任务同时触发）

| 项 | 结果 |
|---|---|
| 构成 | 8 个小库 + 2 个 150MB 级库（各 15 万行）同时触发 |
| 结果 | ✅ **10/10 全部 success** |
| 墙钟 | **15.3s**（并发执行；2C 单机 CPU 为瓶颈） |
| 总产物 | 10.6 MB |

## 三、阶段 C：并发 DB 读写（50 线程 × 20 轮 = 1000 次）

| 项 | 结果 |
|---|---|
| 成功率 | ✅ **1000/1000（0 错误）** |
| 延迟 | P50 **234ms** / P95 **491ms**（SQLite 元库 + busy_timeout 30s，50 并发写排队属预期） |
| 墙钟 | 5.0s |

## 四、阶段 D：并发 + 大数据组合

| 项 | 结果 |
|---|---|
| 构成 | 2 个 150MB 库并发备份 + 同时 50 线程 DB 读写负载 |
| 结果 | ✅ 双双成功（18.2s / 22.8s 并行完成），备份与并发读写互不干扰 |
| RSS | 平台进程峰值 ~50MB（压测客户端进程内含） |

## 五、结论与建议

1. **并发**：10 并发备份 100% 成功；50 线程 DB 读写 0 错误——调度器 reload 锁、SQLite busy_timeout、备份并发控制在当前单机规模下稳定。
2. **大数据量**：100 万行 / 228MB 逻辑量备份恢复全链路 44s 内完成，硬核对一致；支持更大体量（瓶颈为磁盘 IO 与 CPU，内存占用恒定——流式管道设计）。
3. **建议**：生产部署按 README 建议 `gunicorn -w 4 --threads 8`；元库切换 PG/MySQL 后端（v1.4.14 可插拔元数据库）可进一步降低写锁竞争。
4. 复现：`python /root/e2e/stress_1013.py`（阶段 A/B/C/D）、`python /root/e2e/stress_c.py`（阶段 C 单独）。
