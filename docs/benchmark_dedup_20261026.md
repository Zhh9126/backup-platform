# AIDBM 对标"源端去重"能力分析与实现（2026-10-26）

对标输入：中科热备宣传文《买 100T 的备份一体机，为什么只能存 20T 数据？》——核心命题：**源端去重（数据离开源主机前算指纹，重复块不走网络）vs 先写入后去重**；去重率与数据类型强相关，选型必须 POC 实测。

## 一、AIDBM 去重能力现状（实现前）

| 能力 | 状态 | 证据 |
|---|---|---|
| 全局块级去重（落盘后） | 已有：4MB 切片 sha256 内容寻址、`dedup_index` 引用计数、`.dedup_store` 物理块库、全局重删比/累计节省统计，file 引擎备份后自动记账 | core/global_dedup.py、core/engines/file.py `_apply_global_dedup`、api/dedup.py |

| 存储真实节省 | 记账层有（重删比统计）；产物文件本身仍全量落盘（块寻址存储+按需重组未做） | — |

## 二、本轮实现：文件级源端传输去重（v1 已落地）

### 技术路线选择（为什么不用固定块）

先实现了 4MB 固定块流去重（远端 dd+sha256sum 分块指纹），E2E 暴露致命缺陷：**tar/gzip 流式归档中任一文件变化，其后所有块的字节移位**（gzip 头 mtime + 归档偏移），跨轮命中率趋近 0。业界用变长块 CDC（rolling hash）解决，但零 agent 约束下远端无法运行 rolling-hash 程序。**文件级粒度没有移位问题**：未变文件整文件跳过（内容寻址与归档位置无关），日变化率 3% 的场景实传就是 ~3%——正对应文章的账。固定块实现保留在 `pull_assemble_dedup`（适用于"单一大产物文件、前缀稳定"场景，如数据库远端 dump 单文件传输，后续接入）。

### 实现内容

- **core/dedup_source.py**（新增，两条通道）：
  - 文件级（主方案）：`remote_file_manifest`（远端 find+sha256sum+stat 只读清单，零 agent 零临时文件）→ `pull_files_dedup`（比对文件库 `.dedup_store/files/<sha>`，仅新/变文件 SFTP 拉取，拉取后哈希对账）→ `build_tar_from_manifest`（平台侧重建标准 tar.gz，逐成员回读哈希硬核对）。
  - 块级（预留）：`remote_fingerprint` + `pull_assemble_dedup`（dd 分块指纹，跨轮仅传新块，整文件 sha256 对账）。
- **core/engines/file.py**：`_tar_remote_to_local` 挂接 `extra.source_dedup` 通道；任何失败**安全回退**原整包流式通道（正确性不受影响）；统计透出到备份消息（实传/逻辑/节省率/命中/拉取文件数）；源端去重轮自动跳过落盘后重删（防引用计数重复记账）。
- **前端**：file_backup.html「源端传输去重」开关（远程源生效）+ app.js extra 读写（缓存戳 2026102601）。

### 实测结果（本机 SSH 真实通道，/root/e2e/e2e_dedup.py，9/9 PASS）

|---|---|---|---|---|
| 第一轮（建库） | 22.0 MB | 12.0 MB | 45.4% | 10 个同内容文件被文件库立即命中 |
| 第二轮（模拟日变化：改 1 文件 + 新增 1 文件） | 22.0 MB | **1.0 MB** | **95.5%** | 只拉变化的 2 个文件 |

## 三、选型 5 问（文章口径）的 AIDBM 应答

| 问题 | AIDBM 应答 |
|---|---|
| 1. 去重在源端还是目标端？ | 两者都有且**复用同一内容寻址库**：源端文件级去重省带宽（v1 已落地），落盘后全局块级去重记账（原有）。源端方案零 agent——远端只跑 POSIX find/sha256sum/stat，不装任何东西。 |
| 2. 去重率基于什么数据集？ | 不给实验室峰值。**按任务实测**：每轮备份消息实时输出"实传/逻辑/节省率"，用户拿自己的数据跑两轮即得真实数字。诚实边界：数据库 dump（文本重复度高）收益大；已压缩/加密数据收益低（与业界一致）。 |
| 3. 去重和压缩串联还是并联？ | AIDBM 是"源端内容寻址去重 → 平台重建 gzip 产物 → 落盘后块级记账"，压缩发生在去重之后的平台侧，互不干扰（文章说的"先压缩再去重会打折扣"问题不存在——远端不做压缩）。 |
| 4. 有效容量怎么算？ | 当前为**带宽节省实测值**（每轮可见）；存储级真实节省需 v2（块/文件寻址存储+按需重组，替代全量产物落盘）。诚实标注：v1 产物仍全量落盘，宣传口径只承诺带宽节省，不承诺存储节省。 |
| 5. 扩容后去重字典会不会重建？ | 去重库就是内容哈希（sha256）本身，天然分布式无状态——不存在"字典重建"问题；新增平台节点只要能访问同一 BACKUP_ROOT/.dedup_store 即共享命中。 |

## 四、诚实边界与 v2 路线

1. **v1 只承诺带宽节省**（实测可验证），存储节省仍是记账口径——v2 把产物改为"清单+块库"存储、恢复时按需重组，才能兑现"1500TB→150TB"的存储账（涉及恢复/校验/克隆等下游按需物化，需专项）。
2. **文件级粒度的代价**：单个大文件内部少量变化需整文件重传（块级 CDC 是终极解，零 agent 远端不可行；单文件场景可用预留的块级通道按需启用）。
3. **远端成本**：清单扫描需读全量文件算 sha256（源机 CPU/IO 换带宽），文章明确"这个代价和节省的带宽比几乎可忽略"，但海量小文件场景建议用户评估。
4. 当前挂接范围：**文件备份远程源**（全量）；数据库远端 dump 单文件通道、Windows 远端（find 语义差异）为后续接入点。
