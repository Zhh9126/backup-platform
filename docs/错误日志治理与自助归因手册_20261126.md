# AIDBM 错误日志治理与自助归因手册

> 版本：2026-11-26　适用：AIDBM v3.0.0 及以后（含本轮修复）
> 适用场景：客户现场 / 其他平台部署只有一份 `logs/error.log`，需要判断"到底哪件事在反复失败"

---

## 一、日志体系现状（先知道日志在哪、怎么存）

| 文件 | 内容 | 轮转 |
|------|------|------|
| `logs/platform.log` | 全量运行日志（INFO 起） | 单文件 20MB × 10 份（`LOG_MAX_BYTES` / `LOG_BACKUP_COUNT` 可调） |
| `logs/error.log` | **仅 ERROR / CRITICAL**，排查先看这一份 | 同上 |
| `logs/crash.log` | 段错误 / 未捕获异常 / 子线程异常 / 终止信号堆栈 | 追加 |
| `logs/operations/` | 按任务/记录分目录的**详细操作日志**（含命令、退出码、stderr） | 按任务维度 |

四项内建能力（2026-11-26 前的版本没有，需升级）：

1. **重复日志限频**：同一「logger + 消息模板 + 级别」在窗口内只放行一条，重复越多抑制越久（指数退避，默认 300s 起、最长 3600s），窗口到期补一条汇总「同类错误此前已重复 N 次」。
   - 开关 `LOG_DUP_SUPPRESS`（默认开）、`LOG_DUP_WINDOW_SEC`、`LOG_DUP_MAX_WINDOW_SEC`。
   - 观测：页面「系统 → 日志」或 `GET /api/logs` 的 `dup_suppress` 字段（`passed` / `suppressed` / `keys`）。
2. **第三方噪音静默**：`paramiko.transport` 内部握手 Traceback 不再进日志（实测曾占 1966 行）。
3. **脱敏**：口令 / 令牌 / 连接串凭据（`USERID=user/pw@host`、`disql "SYSDBA/pw"@host` 等）在落盘前统一打码成 `***`，日志可安全外发。
4. **测试隔离**：pytest 进程**不再写生产日志目录**（避免测试里的预期异常混进现场 error.log）。

## 二、三步自助归因（现场照做即可）

### 第 1 步：跑分析器

```bash
# 在平台机上（任意部署版本，只需 Python3，无第三方依赖）
python3 <程序目录>/scripts/diag/analyze_error_log.py
# 或分析别处拷来的日志
python3 scripts/diag/analyze_error_log.py /path/to/error.log -n 500 --top 15
# JSON 输出（便于归档/工单）
python3 scripts/diag/analyze_error_log.py --json > err_report.json
```

输出三张表：

1. **按级别 / 按 logger 分布**——先看清是哪一类功能在报错；
2. **按错误模板聚类**——时间、任务号、IP、端口、路径、UUID 全部归一化，"同一条错误的不同次出现"合并为一条（识别刷屏的关键）；
3. **处置建议**——命中内置特征库时给出根因方向与排查动作（只给"下一步查什么"，不臆断结论）。

### 第 2 步：看「刷屏型错误」清单

同一模板出现 ≥ 20 次即为刷屏型。刷屏会淹没真实故障，优先处理：

| 刷屏特征 | 根因 | 处置 |
|---------|------|------|
| `rt.cdc … task=N 启动日志流失败: [CODE:-70028]Create SOCKET connection failure` | **达梦实例未启动 / 端口不通** | 目标机 `dmserver` 进程在不在；端口在 `dm.ini` 的 `PORT_NUM`（**不能用命令行 `-port` 传端口**）；防火墙与连通性 |
| `pg_receivewal: error: incompatible server version X; client does not support streaming from server versions newer than Y` | **平台侧流复制客户端版本 < 服务端** | 平台侧安装与服务端同主版本或更高的 `pg_receivewal`（数据库服务器不装任何工具） |
| `paramiko … banner exchange` / `SSH transport dead` | SSH 通道异常 | 大文件走分离式后台打包；检查中间设备会话时长上限 |
| `errno 28` / `No space left on device` | 磁盘满 | 清历史产物；检查产物与工作目录是否同盘 |
| `[resource_budget] 任务 N 被阻断` | 并发/空间预算保护 | 该类已是 WARNING，不会再刷 ERROR |

### 第 3 步：按动作处置并复核

处置完再看一次 `error.log` 尾部，或在页面看「实时备份健康」/「操作日志」交叉核对。

## 三、错误速查表

| 日志特征 | 根因 | 处置动作 |
|---------|------|---------|
| `1045 / Access denied / ORA-01017` | 凭据错 / 口令过期 | 核对任务账号口令；平台机 `~/.my.cnf` 会覆盖环境变量口令（必须 `--no-defaults`）；Oracle 查 `ORA-28002` |
| `command not found / rc=127` | 客户端工具缺失 | 工具装**平台侧**，数据库服务器零安装；在任务「高级选项 → 工具路径」指定客户端 `bin` 目录 |
| `no pg_hba.conf entry` | 源库未放行复制账号 | 源库增加 `host replication all <平台IP>/32 scram-sha-256` |
| `SCRAM authentication requires libpq version 10 or above` | 平台 libpq 过旧 | 用客户端自带 libpq（平台已按客户端路径自动对齐） |
| `备份盘可用空间 0GB 低于保护阈值 5GB` | 备份盘空间保护 | 清历史产物 / 扩容（阻断是保护行为，不产生坏产物） |
| `UNIQUE constraint / duplicate key` | 迁移或同步重跑 | append 模式会重复写；增量水位是否已持久化 |
| `FileExistsError` / 锁文件残留 | 单实例锁冲突 | 新版用内核字节锁，进程退出自动释放；历史残留锁文件可直接删除 |

### 现场实例日志判读示例（2026-11-26 抽样 500 行）

| 现象（原文） | 判定 | 处置 |
|--------------|------|------|
| `paramiko.ssh_exception.SSHException: Error reading SSH protocol banner`（21 次，**集中在每天 02:00–02:01，连续 4 天，每天 6 次**） | 并发建连打满 sshd `MaxStartups`（定时任务集中触发） | 升级到含第 9 项的版本（握手串行化+退避）；必要时调大 `MaxStartups`；错开 02:00 的任务 |
| `db_type=oracle 暂不支持真实克隆（当前支持 mysql/mariadb/postgresql/kingbase/dameng …）` | **现场部署的是旧版本**（当前版本已支持 oracle 真实克隆） | 升级到最新离线包/镜像后重试 |
| `未处理异常 [POST /api/clone/2/approve]` | 克隆失败冒泡成 500 | 升级后返回 400 + 失败原因 |
| `Java Virtual Machine is not running`（Oracle LogMiner 抽取失败） | 平台侧 JVM 未运行 → JDBC 兜底通道不可用（Oracle 11g 依赖它） | 确认 JRE/JDK 8+ 与 `JAVA_HOME`；重启平台进程；或改用 oracledb thin（12.1+） |
| `[ORACLE核心交易库-…] expdp 不可用，无法执行 Oracle 全量导出` | 本机回退分支的误导性提示（真实原因在远端通道） | 纳管 SSH 主机 + `db_os_user`（默认 oracle）；升级后错误会同时给出远端与本机两侧原因 |

> 判读提示：**先看"错误时间分布"章节**。同一时间点高度规律（每天同一分钟）＝定时任务集中触发，
> 与链路抖动/偶发故障的处置方向完全不同。

### 部署侧需要配合做的事

1. **升级到含上述修复的版本**（本清单第 1–8 项），否则刷屏与停摆类问题会重复出现。
2. **平台侧准备与源库匹配的流复制客户端**（PG 16/17/18 源库需要 ≥16 的 `pg_receivewal`）：
   ```bash
   # 在源库机上找到与服务端同版本的客户端，拷到**平台机**（数据库服务器不装任何备份工具）
   #   /usr/local/pgsql/bin/pg_receivewal  →  平台机 /opt/database/bin/pg_receivewal
   #   /usr/local/pgsql/lib/libpq.so.5.*  →  平台机 /opt/database/lib/
   # 平台会自动按"同目录树优先 + 加载探针验证"挑选 libpq；不匹配时回落平台自带 libpq
   ```
   注意：客户端的 **glibc 需求必须 ≤ 平台 glibc**（实测 CentOS7/glibc 2.17 可跑 PG16 客户端，
   但 PG16 的 libpq 需 GLIBC_2.25 → 不可直接用，需用平台自带 libpq 或 el7 构建的 libpq）。
3. **检查实时保护是否在跑**：页面「实时备份」看健康灯；`GET /api/logs` 的 `dup_suppress.suppressed`
   持续增长说明限频在生效（说明确实有周期性失败在刷屏，需要按第 2 步处置根因）。
4. **达梦实时任务**：`[CODE:-70028]` 一律先查实例是否启动（端口看 `dm.ini` 的 `PORT_NUM`）。

## 五、诚实边界

- 分析器只做**归类与方向提示**，不替代现场判断；处置前请与「备份记录 / 操作日志 / 实时备份健康」交叉核对。
- 限频只**收敛日志量**，不修复根因——根因不处理，功能依然不工作（限频只是让真错误不被淹没）。
- 英文报错中文化覆盖的是已知的 libpq/流复制典型报错，未覆盖的按原文上报（不臆造翻译）。
- 本手册与手册中的修复均已在本机真机验证（PG 16.9 源库流复制由"起不来"恢复为"正常收段"），
  但其他平台的具体环境（glibc、客户端版本、实例状态）仍需按第 4 节逐项核对。
