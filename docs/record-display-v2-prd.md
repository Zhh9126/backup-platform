## 0. 相对 v1 的变更速览

| 维度 | v1（已实现） | v2（本次） |
|---|---|---|
| 展示要素 | **五**要素：业务系统 + IP + 备份类型 + **备份方式** + 备份时间 | **四**要素：业务系统 + IP + 备份类型 + 备份时间（**删除备份方式**） |
| 「业务系统」语义 | 复用 `backup_tasks.name`（v1 §8 Q1 的临时方案） | **独立字段** `backup_tasks.biz_system`，缺失时回退 `name` |
| 数据录入 | 无（借用任务名） | 两个建任务弹窗新增**必填**输入框 |
| `#id` 后缀 | 保留（安全底线） | **保留不变**（见 Q1 待确认其语义） |
| 搜索 | `keyword` LIKE 匹配 `name` / `host` | **扩展**匹配 `biz_system`，否则按业务系统搜索会漏 |

> v1 §8 Q1 曾判断「若用户期望独立业务系统台账，需新增 `backup_tasks.biz_system` 字段 + 表单录入 + 数据回填，建议单独立项」。**本次即为该立项的落地**，v1 Q1 就此关闭。

## 1. 产品目标

1. **业务系统成为一等字段**：让备份记录以「业务视角」而非「任务视角」被识别，运维看到的是"OA 办公系统"，而不是"phase2-demo-mysql"这种任务命名残留。
2. **展示模板全站唯一**：所有消费备份记录的入口收敛为同一套四要素模板，任何新增入口只能调用统一格式化函数，杜绝再次分叉。
3. **零数据迁移的平滑兼容**：存量任务在不做任何回填的前提下，展示、编辑、搜索三条路径均正常工作，不出现空白、不阻塞保存。

## 2. 用户故事

1. **As a** 运维工程师，**I want** 新建备份任务时单独填写「业务系统」，**so that** 我可以给任务起 `mysql-增量-v2` 这种运维向的名字，同时让记录页展示成业务方看得懂的「OA 办公系统」。
2. **As a** 值班主管，**I want** 备份记录页只看到「业务系统 / IP / 备份类型 / 备份时间」四列，**so that** 表格不再被"全量/增量"这种执行细节挤占横向空间，我一眼扫到的都是定位性信息。
3. **As a** 运维工程师，**I want** 系统里 14 个历史任务在我没回填业务系统前照常显示任务名，**so that** 上线当天不会满屏"-"，我可以按自己的节奏逐步补录。
4. **As a** 运维工程师，**I want** 在备份记录页搜索"OA"时，无论该任务的业务系统是填的还是回退任务名的，都能被搜到，**so that** 搜索结果与我眼睛看到的展示文案保持一致。
5. **As a** 运维工程师，**I want** 恢复时下拉里的业务系统名后面仍带 `#id`，**so that** 同一业务系统下的多个备份集我不会选错。

## 3. 字段映射增量（关键结论）

> 以下结论均已通过读代码 + 查实际库（`instance/meta.db`：14 任务 / 89 备份记录 / 12 恢复记录）验证。

| 用户视角术语 | 数据库字段 | 下发字段 | 状态 |
|---|---|---|---|
| **业务系统** | `backup_tasks.biz_system` | `biz_label` | 🆕 **列不存在，需新增**。实测 `PRAGMA table_info(backup_tasks)` 共 42 列，**无 `biz_system`** |
| 任务名称（内部用） | `backup_tasks.name` | `task_name` | ✅ 保留，仅作为回退源与任务管理用途 |
| IP | `backup_tasks.host` → 归一化 | `host_ip` | ✅ v1 已实现（`models.normalize_host_ip`），本次不动 |
| 备份类型 | `backup_records.db_type` | `db_type_display` | ✅ v1 已实现，本次不动 |
| ~~备份方式~~ | ~~`backup_records.backup_type`~~ | ~~`backup_type_display`~~ | ❌ **本次从展示层移除**（字段与接口保留，见 P2-1） |
| 备份时间 | `backup_records.started_at` | `started_at` | ✅ v1 已实现，本次不动 |

### 3.1 回退规则 R2（**本次核心规则**）

```
biz_label = biz_system.strip()  if biz_system 非空
          = name                 否则（存量任务）
          = "-"                  两者皆空（理论不可达，name 为 NOT NULL）
```

**必须由后端统一计算并下发 `biz_label`，前端不得自行判空回退。**
理由：v1 已确立「后端只给归一化结果，前端不得再解析」的约定（见 `record-display-design.md` §6）。回退逻辑一旦在 6 个前端入口各写一遍，必然再次分叉。

**存量数据影响面（实测）**：当前 14 个任务的 `biz_system` **全部为空**，即上线首日 **100% 的记录都会走回退分支**。因此 R2 不是边缘情况兜底，而是**主路径**，必须纳入 P0 与测试用例。

|---|---|---|---|
| 2 | `OA` | `root@192.168.220.150:22` | `OA`（回退） |
| 3 | `mysql-增量` | `192.168.220.150` | `mysql-增量`（回退） |
| 23-30 | `phase2-demo-mysql` ×8 | `127.0.0.1` | `phase2-demo-mysql`（回退，8 条同名） |
| 31 | `123` | `本地` | `123`（回退） |

## 5. UI 设计稿要点

### 5.1 「业务系统」输入框位置

**数据库备份任务弹窗**（`templates/tasks.html`，「基本信息」Tab 首行）

```
┌─ 基本信息 ─────────────────────────────────────────┐
│ 业务系统 *          │ 任务名称 *                    │   ← 新行（各 col-md-6）
│ [OA 办公系统      ] │ [mysql-增量-v2            ]  │
│ 用于记录展示         │ 仅用于任务管理                │
├────────────────────────────────────────────────────┤
│ 数据库类型 * │ 备份类型 * │ 主机地址 * │ 端口 *     │   ← 原首行下移
└────────────────────────────────────────────────────┘
```

**文件备份任务弹窗**（`templates/file_backup.html`，表单首行）

```
┌────────────────────────────────────────────────────┐

├────────────────────────────────────────────────────┤
│ 备份类型            │ 源类型                        │   ← 原首行下移
└────────────────────────────────────────────────────┘
```

**控件规格（两弹窗一致）**

| 项 | 值 |
|---|---|
| id | `#t_biz_system`（DB）/ `#f_biz_system`（文件） |
| label | `业务系统 *` |

## 7. 验收标准

1. **新建**：两个弹窗均出现必填「业务系统」；留空时前端拦截、绕过前端时后端返回 400。
2. **落库**：新建后 `SELECT biz_system FROM backup_tasks WHERE id=?` 能取到填写值（验证 P0-2 白名单确实生效）。
3. **展示**：`/records`、`/restore_records`、`/restore`（下拉 + 详情卡片 + 页内表）、`/datamining`、`/clone` 六处，同一条记录的四要素取值完全一致，且**均无「备份方式」**。
4. **回退**：14 个存量任务在未回填的情况下，上述六处均显示其 `name`，无空白、无 `-`、无 `undefined`。
5. **编辑**：打开任一存量任务的编辑弹窗，业务系统框可正常保存（不被必填校验死锁）。
6. **搜索**：`/records` 与 `/restore_records` 输入业务系统新值、旧任务名、IP 三类关键字均能命中；清空后恢复全量。
7. **布局**：三张表删列后，空数据提示行 `colspan` 与实际列数一致，表格无错位。
8. **不回归**：`templates/protection.html` 的「备份方式」列保持原样。
